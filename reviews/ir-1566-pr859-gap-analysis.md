The failure texts at head are `expected NotTractable, got Execution(HarnessNotInCrate ..)` and `assertion failed: matches!(decide(16), Decision::Refuse { .. })`
- Stale-row behaviour (examined). `TractabilityTable::decide` (`src/kani/tractability.rs:378-405`) skips every row for which `is_current` is false (generator or kernel version differs), and returns `Decision::Run` when no current `not_tractable` row matches. With all 74 shipped rows at `kernel_version: 1` (43 tractable, 31 not_tractable, generator 0.1.0) and `KERNEL_VERSION = filament_exact::KERNEL_VERSION = 2`, the shipped table refuses nothing. That is FR-056-AC-7 as specified: a stale row is ignored and the clause runs. It does not fall back to another table and does not refuse. Nothing can be wrongly accepted as proved: `Run` only lets generation proceed, and the verdict still comes from the Kani run. A clause the table measured as intractable is now generated and run until timeout or memory exhaustion (an Inconclusive, non-proof outcome) instead of being refused before generation. The shipped table is opt-in (`shipped_general_route_scalar`, FR-056-AC-15). The PR body states that the rows are stale and ignored. No AC, spec row or qualification doc does.

## Verdict

The pin move leaves 42 failing tests that pass on main, and their causes are what the coder reported. A float64 `=` is now refused at FSL emission, and the shipped IR-1530 table is entirely stale under kernel 2. These are real regressions in shipped capability, not test noise: float scalar and enum scalar harness generation from source with a float `=` no longer works, and the shipped general-route refusal is inert. The lead has asked the planner how to handle them. This review only records them and makes no decision. Two spec rows are now false: FR-018-AC-50 describes FSL emitting the float call, and FR-015-AC-129 still names the QSL-1901 blocker.
