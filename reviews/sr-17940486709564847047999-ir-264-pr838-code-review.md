## Summary

Ticket: IR-264 (PR2 of the composite-equality shadow work; IR-241's shadow machinery is
delivered through this route). The PR adds a bounded-shadow generator over a two-leaf stand-in
family (`shadow.rs`), a `syn`-based parsed-source check (`source_check.rs`), a pure refinement
planner and proof-strength mapping (`refinement.rs`), a native refinement execution entry that
reuses FR-017's bounded launcher (`execute/refinement.rs`), and a `Shadow` variant of
`KaniExecutableHarness`.

What was checked, by reading and by reproduction:

- FR-028-AC-13 in the generator: the rendered harness is a fixed template; the generator calls
  `check_shadow_source` with the abstraction module forbidden, refuses any loop construct, and
  compares the assumed draws parsed from source with the identity's drawn bounds. The shadow and
  proof modules name no `filament_contract_runtime` / `filament_exact` path and no stub. The
  three AC-13 mutants in the test (runtime `use`, `kani::stub` / `stub_verified`,
  `kani::assume(left == right)`) are real generator mutations through `Hooks` and each is
  refused by the check. The check itself has false negatives (FND-001).
- FR-028-AC-17: `proof_strength` cannot return `ProductionProved` for `BoundedShadow` (the match
  arm for `ProductionProved` is reachable only with `ProofSubject::Production`); a disagreement
  returns `RefinementFailed` before the verified gate, so a verified shadow beside a disagreement
  is `refinement_failed`.
- The refinement driver: every planned case runs; construction refusal, `Refused`, `Incomplete`
  and observable mismatch are each a disagreement; `execute_kani_refinement` refuses a report
  whose case count differs from the plan, so no case is silently skipped.
- `execute.rs` touch is two lines (module + re-export). The `Shadow` arm in `harness.rs` is
  additive; every existing arm is unchanged.
- The installed-Kani test calls `KaniInstallation::discover()` and `execute_kani_obligation`
  over a real generated crate: it is a real Kani run, not a stand-in. `Verified` requires every
  cover satisfied (`classify.rs:276-280`). The shared-helper control (`pair_count` mutated to 2
  verifies) is meaningful: it demonstrates that the shadow and its expectation share the helper,
  so the proof is blind to that mutant, which is exactly why AC-18/AC-22 route it to the
  refinement run or the independent check; the refinement test then catches it.

Reproduction of FND-001: `source_check.rs` copied verbatim into a scratch crate with
`syn = "=2.0.119"`, run against the generator's harness shape plus each bypass; results in
Findings.

## Verdict

The machinery is correct on its main paths: the strength mapping can never yield
`production_proved` for a shadow, disagreements are never skipped, the case plan matches AC-16's
boundary rule for integer leaves, the refinement entry reuses FR-017's launcher and records
ceilings, peak and versions, and the installed-Kani test is a real backend run whose
shared-helper control is meaningful. The `execute.rs` / `harness.rs` changes do not alter any
existing arm, but they break the crate's layering (FND-005) and the shadow template escapes the
cover-last inspection (FND-006): four `--test it` structural tests fail that pass on
origin/main. Not mergeable until FND-005, FND-006, FND-001 and FND-002 are fixed in this PR;
FND-003 and FND-004 are low and may ride the same round.
